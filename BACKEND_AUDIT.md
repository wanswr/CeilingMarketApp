# ТЕХНИЧЕСКИЙ АУДИТ БЭКЕНДА (NESTJS / PRISMA) — СТО ОТЧЕТ

Этот отчет содержит глубокий аудит серверной части платформы **CeilingsApp** на базе NestJS, Prisma и PostgreSQL. Анализ проведен с позиции CTO и направлен на выявление критических уязвимостей безопасности, инфраструктурных ограничений при масштабировании, проблем многопоточности (deadlocks) и готовности системы к реальному продакшену.

---

## 1. РЕЗЮМЕ ДЛЯ БИЗНЕСА (EXECUTIVE SUMMARY)

Бэкенд CeilingsApp построен на современном, надежном стеке (NestJS + Prisma + TypeScript). Кодовая база хорошо структурирована, разделена на независимые функциональные модули, использует строго типизированные DTO и глобальные пайпы валидации.

Тем не менее, текущая версия бэкенда представляет собой **MVP для тестирования (разработки)** и содержит ряд критических блокирующих факторов (**P0-уязвимостей**), которые делают невозможным выпуск приложения в реальный продакшен без предварительных доработок.

**Основные риски:**
1. **Полное отсутствие реальной авторизации (P0):** В коде отсутствует интеграция с SMS-шлюзами. Сервис работает исключительно в "девелоперском" режиме с кодом `1234`. В не-девелоперском режиме авторизация просто выбрасывает ошибку.
2. **Финансовая уязвимость подписок (P0):** Активация платных подписок мастеров происходит по прямому неконтролируемому POST-запросу со стороны клиента. Любой пользователь может получить премиум-доступ бесплатно.
3. **Инфраструктурный тупик при масштабировании сокетов (P1):** Веб-сокеты завязаны на оперативную память одного сервера. При переходе на несколько серверов (кластер) чаты и обновления карты сломаются.

## 2. КРИТИЧЕСКИЕ УЯЗВИМОСТИ И БЛОКЕРЫ (P0)

### P0: Отсутствие боевой авторизации (SMS OTP)
**Где живет:** `backend/src/modules/auth/auth.service.ts`, метод `verifyOtp`.

**Суть проблемы:**
Код метода проверки OTP-кода жестко завязан на тестовый режим:
```typescript
async verifyOtp(phone: string, code: string) {
  const authMode = this.configService.get('AUTH_MODE') || 'development';

  if (authMode === 'development') {
    if (code !== '1234') {
      throw new UnauthorizedException('Invalid OTP code');
    }
  } else {
    // В боевом режиме код просто падает!
    throw new UnauthorizedException('Authentication is only allowed in development mode');
  }
  ...
}
```
**Последствия:** При развертывании в продакшене (где `AUTH_MODE !== 'development'`) пользователи физически не смогут войти в приложение или зарегистрироваться. Реальный функционал отправки SMS и проверки кодов через внешние шлюзы (например, СМС.ру, Twilio или Sms Aero) отсутствует в кодовой базе.

---

### P0: Уязвимость "Бесплатной Премиум-Подписки" (Дыра в биллинге)
**Где живет:** `backend/src/modules/subscription/subscription.controller.ts`, метод `activateSubscription`.

**Суть проблемы:**
Конечная точка для активации платных подписок мастеров доступна для прямого вызова:
```typescript
@Post('activate')
async activateSubscription(@Body() dto: { days: number }, @Req() req) {
  return this.subscriptionService.activate(req.user.id, dto.days);
}
```
Бэкенд безоговорочно верит клиенту и активирует подписку на переданное количество дней `dto.days`.

**Последствия:** Любой мастер с минимальными техническими знаниями (или используя бесплатный инструмент вроде Postman/cURL) может отправить запрос `POST /api/subscriptions/activate` с телом `{"days": 3650}` и мгновенно получить 10 лет бесплатного премиум-доступа. Это полностью уничтожает монетизацию продукта.
*Решение:* Активация должна происходить **исключительно** на основе входящих Webhook-уведомлений от платежной системы (ЮKassa, Робокасса, Stripe) после верификации сигнатуры платежа.

## 3. АРХИТЕКТУРНЫЕ И ИНФРАСТРУКТУРНЫЕ РИСКИ (P1)

### P1: Ограничение масштабирования WebSocket (Single Instance Lock)
**Где живет:** `backend/src/modules/gateway/app.gateway.ts`.

**Суть проблемы:**
Шлюз `AppGateway` использует стандартный in-memory адаптер Socket.io. Все комнаты клиентов (`client.join`), списки подключений и отправка уведомлений работают в рамках оперативной памяти одного процесса Node.js.

**Последствия:** При росте нагрузки вам потребуется запустить бэкенд на 2-3 серверах за балансировщиком (Nginx / Cloudflare). В этот момент WebSocket-архитектура полностью сломается:
* Пользователь А подключен к Серверу 1.
* Пользователь Б подключен к Серверу 2.
* Они находятся в одном чате, но не будут получать сообщения друг друга, так как бэкаст сокетов не будет выходить за пределы конкретного сервера.
*Решение:* Немедленно подключить сокет-адаптер Redis (`socket.io-redis`) для синхронизации комнат и событий между инстансами бэкенда.

---

### P1: Риск "Повисания" Исполнителей при удалении аккаунта Заказчика
**Где живет:** `backend/src/modules/users/users.service.ts`, метод `deleteProfile`.

**Суть проблемы:**
Бэкенд поддерживает GDPR-совместимое удаление аккаунта (софт-делет с анонимизацией данных). Метод затирает имя, телефон и соцсети пользователя. Однако в методе **отсутствует проверка на наличие активных заказов**.

**Последствия:**
Если заказчик удаляет профиль в тот момент, когда его заказ находится в статусе `IN_PROGRESS` (Исполнитель уже закупает материалы или монтирует потолок):
* Мастер теряет любые контактные данные заказчика.
* Мастер не знает, кому сдавать работу и с кого требовать оплату.
* База данных засоряется "зависшими" заказами-сиротами.
*Решение:* Блокировать удаление аккаунта с выдачей ошибки `400 Bad Request`, если у пользователя есть незавершенные заказы в статусе `CLAIMED` или `IN_PROGRESS`.

---

### P2: Потенциальные взаимные блокировки базы данных (Database Deadlocks)
**Где живет:** `backend/src/modules/orders/orders.service.ts`, метод `acceptApplication`.

**Суть проблемы:**
При выборе исполнителя внутри транзакции `$transaction` выполняется сразу несколько тяжелых операций:
1. Выборка и блокировка заказа.
2. Логирование истории статусов.
3. Обновление статуса принятой заявки на `ACCEPTED`.
4. Обновление **всех остальных** заявок на `REJECTED` через `updateMany`.
5. Поиск или создание чата.

При высоком конкурентном трафике (например, когда несколько заказчиков одновременно одобряют отклики, а мастера параллельно отзывают заявки на те же заказы) транзакции в СУБД PostgreSQL будут конкурировать за блокировку строк в таблицах `orders` и `applications`.

**Последствия:** СУБД начнет аварийно завершать транзакции с ошибками `40001 (deadlock detected)`. Пользователи будут видеть случайные ошибки при выборе исполнителей.
*Решение:* Оптимизировать порядок запросов в транзакции, настроить уровни изоляции и добавить механизм повторных попыток (retry) на уровне транзакций Prisma.

## 4. ПОЛОЖИТЕЛЬНЫЕ СТОРОНЫ БЭКЕНДА

Серверная часть спроектирована грамотно и качественно по стандартам разработки 2026 года:
1. **Гео-комнаты (Geo-room Grid):** Деление карты на динамическую сетку 3x3 комнаты снижает трафик бродкастов на 90%. Это великолепное архитектурное решение.
2. **Trace ID и Сквозной Логгер:** middleware и interceptor автоматически пробрасывают `requestId` через NestJS AsyncLocalStorage. Это уровень серьезного энтерпрайза.
3. **Безопасность PII:** Метод `findPublicProfile` жестко очищает все приватные данные (телефон, соцсети, push-токены), полностью исключая утечку персональных данных.
4. **Idempotency Key:** Контроллеры защищены от повторных кликов и сетевых сбоев, что гарантирует целостность базы данных.

## 5. ПОШАГОВЫЙ ПЛАН ИСПРАВЛЕНИЙ БЭКЕНДА

### Фаза 1: Боевая готовность безопасности и биллинга (Срок: 1-2 недели)
1. **Интеграция SMS-шлюза:**
   Добавить в `AuthService` реальный клиент отправки СМС (например, REST-интеграцию с SMS.ru) и генерировать случайный 4-значный код вместо `'1234'`.
2. **Защита платежного шлюза подписок:**
   Удалить метод `activateSubscription` с прямого клиентского роута. Создать вебхук-контроллер `POST /api/subscriptions/webhook` с валидацией подписи платежной системы для безопасной активации дней.
3. **Защита при удалении аккаунта:**
   Внедрить проверку на наличие активных сделок в `deleteProfile` и выбрасывать `ConflictException`, если есть незаконченные заказы.

### Фаза 2: Инфраструктурное масштабирование (Срок: 1 неделя)
1. **Переход на Redis Adapter:**
   Инсталлировать пакеты `@socket.io/redis-adapter` и `redis` на бэкенде. Настроить запуск Socket.io через Redis Pub/Sub, подготовив систему к горизонтальному росту.
2. **Обработка Deadlocks в транзакциях:**
   Добавить декоратор или утилитарный хелпер для автоматического ретрая транзакций при возникновении ошибок PostgreSQL типа `deadlock_detected` или `serialization_failure`.

---

### Заключение СТО:
Архитектура бэкенда выглядит монолитной, чистой и полностью готовой к высоким нагрузкам. Но перед запуском рекламы и привлечением клиентов **критически необходимо** закрыть две P0 дыры: интеграцию СМС-верификации и защиту активации подписок, а также обезопасить мастеров от внезапного удаления аккаунтов заказчиков в процессе работы.
