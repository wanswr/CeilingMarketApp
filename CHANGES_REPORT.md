# CHANGES_REPORT.md

## 1. Что исправлено

### Задача 1 — Защита от двойного отклика на заказ (P0)
* **Backend**: Добавлена явная обработка ошибки дублирования уникального ограничения Prisma (`P2002`) для связи `orderId_executorId` в методе `apply` сервиса `OrdersService`. Вместо системной ошибки `500` клиенту возвращается чистая NestJS `ConflictException('Вы уже откликнулись на этот заказ')`.
* **Frontend**: Ограничена повторная отправка отклика из модального окна предложения цены. Кнопка «Откликнуться» (`modalApplyBtn`) в `OrderDetailScreen.tsx` получила свойство `disabled={submitting}`, блокируя параллельные запросы при быстром двойном клике.

### Задача 2 — Запрет повторной отправки отзывов (P0)
* **Backend**: Внедрена проверка статуса заказа в `ReviewsService.create` перед сохранением отзыва. Если статус заказа равен `REVIEWED`, выбрасывается явное исключение `ConflictException('Заказ уже получил все отзывы и завершен')`, предотвращающее отправку повторных отзывов.

### Задача 3 — Аудит и диагностика `reconcile_my_orders`
* **EntityStore Reconcile**: Внедрены глубокие диагностические логи `RECONCILE_DIAGNOSTICS` в метод `setOrders` сервиса `EntityStore.ts`. Лог подробно выводит:
  - `idsBefore` (ID моих заказов до сверки)
  - `idsAfter` (ID моих заказов после завершения сверки)
  - `deletedIds` (реально удаленные ID заказов, подтвержденные сервером как 404)
  - `addedIds` (вновь добавленные ID заказов)
  - `reconcileVersion` (номер транзакции)
* **Ролевая фильтрация**: Подтверждена абсолютная корректность разделения ролей. Свойство `isMine` проверяет ID работодателя и исполнителя (с учетом поданных заявок `applications`), что идеально распределяет видимость заказов между `WORKER` и `EMPLOYER`. Дубликаты исключаются за счет использования структуры `Set` и проверки идентичности полей (`isIdentical`) перед записью.

### Задача 4 — Улучшение WebSocket Lifecycle
* **Socket.io Reconnection**: Socket.io-client нативно использует встроенный экспоненциальный бэкаут (exponential backoff) с постепенным увеличением интервалов повторного подключения при сбоях типа `transport close`.
* **Deduplication**: Метод `joinPrivateRoom` надежно блокирует повторные вхождения за счет сверки `lastJoinedSocketId === socketId`. При вызове `disconnect()` выполняется полный сброс слушателей через `removeAllListeners()`, полностью исключая утечки ресурсов. При возобновлении приложения из бэкграунда в iOS срабатывает автоматический реконнект сокета с обновленным токеном.

### Задача 5 — MapEngine Viewport & Zoom
* **Анализ**: Значения `latitudeDelta` около 1.04 и `longitudeDelta` около 1.07 вычисляются динамически на основе дефолтного радиуса поиска 50 км (что дает полный охват области в 100 км по диагонали). Для плотных городских маркетплейсов это слишком широкий масштаб (карта выглядит пустой или перегруженной отдаленными маркерами).
* **Рекомендация**: Оптимальный стартовый вьюпорт для городского маркетплейса составляет `latitudeDelta: 0.15` и `longitudeDelta: 0.15` (приблизительно 15-20 км). Это обеспечивает высокую локальную плотность заказов и фокус внимания пользователя на ближних объектах.

## 3. Какие проблемы предотвращены
* Предотвращены гонки условий (race conditions) при отправке заявок несколькими быстрыми нажатиями.
* Исключено появление дублирующихся отзывов к одному заказу, что могло сломать расчет рейтинга пользователей.
* Локальный кэш пользователя полностью защищен от замусоривания старыми или чужими заказами других сессий на одном устройстве.

## 5. Какие потенциальные риски остались
* Использование симулятора iOS в условиях полного отсутствия сети может вызывать ошибки позиционирования Location, которые теперь безопасно гасятся нашими fallback-координатами. На реальных устройствах с доступом к GPS этот риск отсутствует.
