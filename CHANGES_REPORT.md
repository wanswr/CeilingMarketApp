## 1. ЧТО ПОДТВЕРЖДЕНО КАК УЖЕ РАБОТАЮЩЕЕ (ЗАДАЧИ 1, 2, 4)

### **Задача 1: Защита от двойного отклика (P0)**
* **Prisma Constraint:** В файле `backend/prisma/schema.prisma` на модели `Application` успешно применен составной уникальный индекс `@@unique([orderId, executorId])`. База данных на физическом уровне исключает дублирование откликов исполнителя на один и тот же заказ.
* **Backend Error Handling:** Метод `OrdersService.apply` осуществляет упреждающую проверку существования отклика (`findUnique`) и выбрасывает NestJS `ConflictException('Already applied')` (HTTP 409). Кроме того, мы внедрили явный перехват ошибки `P2002` в блоке `catch`, гарантирующий, что при микросекундной гонке запросов (Race Condition) сервер вернет чистый HTTP 409 (ConflictException), а не упадет в 500 ошибку.
* **Frontend UI Locks:** Экран `OrderDetailScreen.tsx` (в методе `submitOffer`) использует многоуровневый замок:
  1. Локальный флаг `submitting` мгновенно блокирует повторные клики.
  2. Сессионный кэш-сет `activeApplications.has(orderId)` предотвращает параллельные отправки.
  3. Нативная кнопка получает свойство `disabled={submitting}`, блокируя любые действия во время выполнения запроса. Повторные ответы обрабатываются выводом чистого Alert-сообщения без падения интерфейса.

### **Задача 2: Защита от повторных отзывов (P0)**
* **Prisma Constraint:** В схеме Prisma для модели `Review` задано ограничение `@@unique([orderId, authorId])`. Один пользователь может оставить строго один отзыв на один заказ.
* **Backend Error Handling:** Метод `ReviewsService.create()` содержит:
  - Проверку на статус заказа (`order.status === OrderStatus.COMPLETED`).
  - Проверку на существование отзыва автора до транзакции.
  - Обработку ошибки `P2002` (PrismaClientKnownRequestError) в транзакции с пробросом `ConflictException('You have already left a review...')`, что гарантирует отсутствие 500-х ошибок.
* **Frontend UI Locks:** В `OrderDetailScreen.tsx` метод `submitReview` содержит двойную защиту:
  1. Блокировку через `submitting` и коллекцию `activeReviews.has(orderId)`.
  2. После успешной отправки отзыва локальный стейт `order.reviews` мгновенно обновляется, скрывая форму и модалку для отправки отзыва навсегда (`(order?.reviews || []).some(...)` становится `true`). Кнопка повторного открытия формы становится недоступной.

### **Задача 4: Жизненный цикл WebSockets (SocketService.ts)**
* **Exponential Backoff:** Подтверждено. При инициализации сокета передаются параметры: `reconnectionDelay: 1000` (стартовая задержка 1с) и `reconnectionDelayMax: 10000` (максимальная задержка 10с) при бесконечных попытках (`reconnectionAttempts: Infinity`). Socket.io автоматически наращивает задержку, исключая перегрузку сервера.
* **Защита от параллельных connect():** Подтверждено. Метод `connect()` проверяет существование и статус текущего сокета. Если сокет уже подключен к тому же URL, повторное создание сокета игнорируется, предотвращая утечки ресурсов.
* **Очистка listeners при disconnect:** Подтверждено. Метод `disconnect()` вызывает `this.socket.removeAllListeners()`, гарантируя, что старые слушатели удаляются и не создают утечек памяти.
* **iOS Wake Reconnection:** Подтверждено. Реализован слушатель `AppState` в `AuthContext.tsx`. При выходе приложения из фона на iOS (переход в `active`) срабатывает `checkAuth()`, который вызывает `socketService.connect(..., 'auth_sync')`. Внутри `SocketService` при таком событии сокет принудительно дисконнектится для очистки "зомби"-состояний TCP (zombie sockets) и устанавливает новое чистое соединение.
* **Heartbeat:** Отдельный кастомный heartbeat поверх встроенного `engine.io ping/pong` **не нужен**. Дефолтного пинг-понга socket.io полностью достаточно. Дополнительный heartbeat будет лишний раз будить процессор мобильного устройства, разряжая батарею и генерируя паразитный трафик.

## 2. ЧТО РЕАЛЬНО ИСПРАВЛЕНО (ПЯТЬ ТОЧЕЧНЫХ ФИКСОВ)

1. **Безопасность Mass Assignment в `orders.service.ts`:**
   - **Что было:** create() и update() напрямую спредили DTO-объекты в базу данных (`{...dto}`), что создавало критическую уязвимость перезаписи служебных полей базы.
   - **Что сделано:** Вернули строгий явный allowlist/whitelist. При создании разрешены только поля: `title`, `address`, `latitude`, `longitude`, `date`, `price`, `details`, `workType`, `images`, `categoryId` (все системные поля, такие как статус и id создателя, выставляются строго сервером). При обновлении разрешены только поля: `title`, `details`, `address`, `price`, `date`, `images` (статус меняется строго через валидатор переходов `validateTransition`).
2. **Лимит санирования сообщений в `chats.service.ts`:**
   - **Что было:** Сообщения длиной от 2001 до 4000 символов успешно проходили валидацию DTO на клиенте/сервере, но при сохранении тайно обрезались сервером до 2000 символов без уведомления отправителя.
   - **Что сделано:** Добавлена и настроена функция `sanitizeText(text, maxLen = 4000)` в `chats.service.ts`. Теперь лимит санирования совпадает с DTO (4000 символов), гарантируя полную сохранность длинных рабочих сообщений.
3. **Очистка стейта в `EntityStore.clear()`:**
   - **Что было:** При выходе из аккаунта (logout) или смене пользователя в сторе зависали старые значения флагов `isMyOrdersLoaded`, `isInitialLoaded` и `loadedBounds`, что приводило к утечке приватных гео-данных старого пользователя новому.
   - **Что сделано:** Добавили в метод `clear()` полный сброс всех этих свойств: `this.isMyOrdersLoaded = false`, `this.isInitialLoaded = false`, `this.loadedBounds = null`.
4. **Маскирование токенов в логах:**
   - **Что было:** В отладочных логах `RECONCILE_DEBUG` и `[MapEngine] syncMap diagnostic check` записывался срез реального JWT пользователя (`token.substring(0, 8)`), который мог быть сохранен в долговечном лог-хранилище устройства.
   - **Что сделано:** Внедрена неинвертируемая хеш-функция `simpleHash` (алгоритм djb2, возвращающий безопасный 8-символьный hex). В логи пишется только хеш токена, что исключает утечку частей JWT, сохраняя возможность корреляции сессий в дебаге.
5. **Оптимизация обращений к SecureStore в `MapEngine.ts`:**
   - **Что было:** При каждом движении/зуме карты метод `syncMap()` вызывал нативный мост `SecureStore.getItemAsync('userToken')`. Это создавало избыточную нагрузку на Keychain/Keystore нативного устройства при частом панорамировании.
   - **Что сделано:** Реализовано кэширование токена в памяти (`cachedToken` внутри `MapEngine`). Токен считывается из Keychain ровно один раз при первом старте. При логине/логауте/обновлении кэш в памяти синхронизируется через AuthContext, полностью избавляя карту от Keychain round-trips.

## 3. РЕЗУЛЬТАТ АНАЛИЗА RECONCILE (ЗАДАЧА 3)

Анализ логов расхождения `localCount` (локальное количество моих заказов) и `responseCount` (количество заказов в ответе сервера `/orders/my`) показал, что **логика примирения (reconciliation) абсолютно корректна, а расхождения в логах ожидаемы и естественны** по следующим причинам:

1. **Локальное оффлайн-хранилище (Offline-First Cache):** Клиентский `EntityStore` сохраняет завершенные, отмененные или архивные заказы локально для обеспечения возможности просмотра истории в оффлайн-режиме. В то же время серверный эндпоинт `/orders/my` возвращает только активные заказы или заказы, требующие действий на текущий момент. Отсюда возникает разница: `localCount` логично больше, чем `responseCount`.
2. **Асинхронная верификация удалений (Lazy Garbage Collection):** Когда сервер не возвращает заказ в списке `/orders/my`, который локально числится в `myOrders`, `EntityStore` не удаляет его мгновенно во избежание ложных чисток при сетевых сбоях. Вместо этого в фоне асинхронно запускается проверочный запрос `apiService.getOrderDetails(id)`. Только если сервер явно отвечает ошибкой **404 (Not Found)**, этот заказ удаляется из локального стора через `removeOrder()`.
   - *Важно:* Отладочный лог `RECONCILE_DEBUG` записывается **до** начала выполнения этих асинхронных запросов проверки. Удаления происходят позже, поэтому расхождение видно в текущем логе, но устраняется к моменту следующей проверки.
3. **Многоролевая архитектура:** Свойства `myOrders` наполняются на основе полей `employerId`, `executorId` и заявок в массиве `applications` для текущего `currentUserId`. Эта логика учитывает как роли работодателя (`EMPLOYER`), так и исполнителя (`WORKER`) в равной степени, гарантируя консистентность стейта на одном устройстве.
4. **Уникальность ключей:** Использование структур `Map` (`ordersById`) и `Set` (`myOrders`) полностью исключает появление дубликатов заказов в памяти приложения.

## 4. ПРЕДЛОЖЕНИЕ ПО VIEWPORT (ЗАДАЧА 5) — К ПОДТВЕРЖДЕНИЮ

### **Текущая проблема:**
При вычислении дельт в `MapScreen.tsx` используется `CONFIG.DEFAULT_SEARCH_RADIUS_KM` (50 км) для определения области видимости.
Это дает `latitudeDelta` около **1.04** и `longitudeDelta` около **1.07**, что означает, что карта при первом входе показывает область шириной более **100 километров**!
Это приводит к перегрузке рендеринга (отображаются сотни накладывающихся друг на друга пинов) и ухудшает UX (пользователь видит всю Московскую область вместо своего района).

### **Предложение по улучшению (Viewport Proposal):**
Мы предлагаем уменьшить начальный визуальный охват карты, сделав его более сфокусированным и локальным, сохранив при этом фоновый радиус запросов к API.

1. **Разделение дельт для ролей:**
   - **Для Исполнителя (WORKER):** Оптимальный начальный радиус видимости — **10 км** (диаметр 20 км). Это позволяет сразу увидеть ближайшие заказы в своем округе.
     - `latitudeDelta = 0.18`
     - `longitudeDelta = 0.32`
   - **Для Заказчика (EMPLOYER):** Оптимальный начальный радиус видимости — **5 км** (диаметр 10 км). Это дает четкую детализацию улиц вокруг его объекта.
     - `latitudeDelta = 0.09`
     - `longitudeDelta = 0.16`
2. **Как это настроить в коде:**
   Внутри `loadMapData` в `MapScreen.tsx` заменить статический расчет на ролевой:
   ```typescript
   const isWorker = currentUser?.role === 'WORKER';
   const visualRadiusKm = isWorker ? 10 : 5; // Более точный фокус вместо 50 км!

   const totalRangeKm = visualRadiusKm * 2;
   const latDelta = totalRangeKm / 111;
   const lonDelta = totalRangeKm / (111 * Math.cos(loc.coords.latitude * Math.PI / 180));
   ```
   *Результат:* Скорость отрисовки карты вырастет в разы, пины не будут сливаться в огромные нечитаемые гроздья, а интерфейс станет отзывчивым и понятным.
