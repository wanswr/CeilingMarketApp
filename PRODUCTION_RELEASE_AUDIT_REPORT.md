## 1. Общая оценка проекта: 7.5 / 10

Архитектура маркетплейса **CeilingsApp** спроектирована на высоком профессиональном уровне. В приложении реализована реактивная, viewport-ориентированная модель синхронизации данных, а критически важный WebSocket-слой в текущей ветке был эволюционирован до спецификации **V12**, исключающей утечки памяти, дублирование подключений и избыточный глобальный широковещательный трафик.

### Главные архитектурные достижения проекта:
1. **Энергоэффективный и масштабируемый WebSocket-слой (V12)**: Метод `broadcast` в `AppGateway` больше не забивает каналы связи клиентов глобальным вещанием. Он интеллектуально маршрутизирует сообщения: по географическим комнатам-плиткам 3х3 (`geo:lat:lng`) для карты, либо напрямую в приватные комнаты участников сделки (`user:userId`). Клиентская часть в `SocketService.ts` реализует строгую UUID-дедупликацию событий и реестр локальных мутаций для предотвращения эффекта "эха".
2. **Viewport-реактивный MapEngine**: Камера карты в реальном времени управляет подписками на гео-комнаты, а дебаунс в 300 мс предотвращает лавинообразные запросы к API при перемещении карты.
3. **Безопасность профилей**: В `UsersController` успешно закрыта уязвимость Mass Assignment путем внедрения строго валидированного DTO (`UpdateUserProfileDto`), защищающего поля `rating`, `completedOrders` и `isVerified` от несанкционированного изменения через `PATCH /users/profile`.

Тем не менее, **приложение НЕ готово к публичному выпуску в App Store и Google Play**. Обнаружен ряд критических проблем (Blockers) на уровне бизнес-логики, соблюдения гайдлайнов Apple и инфраструктуры медиафайлов.

## 2. Critical Issues (Блокируют релиз / Blocker)

### Issue 2.1: Отсутствие SDK для отправки реальных Push-уведомлений
*   **Файл**: `backend/src/modules/notifications/notifications.service.ts`, `backend/prisma/schema.prisma`
*   **Причина**: Текущая реализация системы уведомлений является "номинальной". Класс `NotificationsService` лишь создает записи в таблице `Notification` в базе данных PostgreSQL. Отсутствует интеграция с внешними сервисами доставки пушей — Apple Push Notification service (APNs) и Google Cloud Messaging / Firebase Cloud Messaging (FCM).
*   **Последствия**: Мобильные пользователи не будут получать никаких уведомлений, когда приложение свернуто или телефон заблокирован. Основная маркетплейс-петля обратной связи (Заказчик разместил заказ -> Мастер откликнулся -> Заказчик выбрал мастера) будет разорвана. Это приведет к катастрофически низкому удержанию пользователей (Retention) и потере базы в первый же день.
*   **Решение**:
    1. На бэкенде интегрировать библиотеку `expo-server-sdk` для NestJS.
    2. Извлекать `pushToken` пользователя из таблицы `User` и отправлять реальные пуш-уведомления на сервера Expo Push Service при создании записей в `NotificationsService`.
    3. На клиенте реализовать запрос разрешений через `expo-notifications` и передавать полученный токен на бэкенд при авторизации.

### Issue 2.2: Отсутствие возможности удаления аккаунта и нарушение каскадных правил в БД (App Store Rejection Risk)
*   **Файлы**:
    - `backend/src/modules/users/users.controller.ts` (отсутствует метод `DELETE`)
    - `backend/prisma/schema.prisma` (модели `Review` и `Chat` привязаны к `User` без правил каскадного удаления)
*   **Причина**: Согласно правилу Apple App Store Review Guideline 5.1.1(v), если приложение поддерживает создание учетной записи, оно в обязательном порядке должно предоставлять пользователю возможность её удаления непосредственно из приложения. В API бэкенда отсутствует эндпоинт `DELETE /users/profile`. При попытке вручную удалить запись пользователя из таблицы `User`, СУБД выбросит ошибку `Foreign key constraint violation`, поскольку таблицы `Review` (authored/received) и `Chat` (employer/executor) не имеют каскадных связей (`onDelete: Cascade`) с моделью `User`.
*   **Последствия**: Гарантированное отклонение приложения цензорами Apple при первой же попытке публикации. Невозможность соблюдения законов о защите персональных данных (GDPR / ФЗ-152).
*   **Решение**:
    1. Обновить `schema.prisma`, добавив `onDelete: Cascade` (или `SetNull` с анонимизацией) для связей `Review.author`, `Review.target`, `Chat.employer`, `Chat.executor`, `Message.sender`.
    2. Реализовать метод `remove(id)` в `UsersService` и вызывать его через новый эндпоинт `DELETE /users/profile`.
    3. Добавить кнопку "Удалить аккаунт" в настройки профиля на мобильном клиенте.

### Issue 2.3: Отсутствие Multipart API для загрузки медиафайлов и клиентского сжатия изображений
*   **Файлы**: `backend/src/modules/orders/orders.controller.ts`, `backend/src/modules/users/users.controller.ts`, `src/screens/CreateOrderScreen.tsx`
*   **Причина**: Маркетплейс предполагает загрузку фотографий потолков для заказов и аватаров пользователей. Однако бэкенд не имеет эндпоинтов для приема `multipart/form-data` и не интегрирован с облачными хранилищами (AWS S3, MinIO или Яндекс.Облако). На фронтенде при выборе фото через `expo-image-picker` отсутствует предварительное сжатие.
*   **Последствия**: Передача тяжелых несжатых Base64-строк напрямую в JSON-телах запросов приведет к перегрузке оперативной памяти мобильных устройств, высокому потреблению трафика и ошибкам сервера `413 Payload Too Large` при отправке фотографий высокого разрешения с современных камер (108MP+).
*   **Решение**:
    1. На бэкенде подключить `NestJS Multer` и модуль `@aws-sdk/client-s3` для загрузки изображений в S3-совместимое объектное хранилище.
    2. Передавать в БД только URL-адреса загруженных файлов.
    3. На мобильном клиенте интегрировать библиотеку `expo-image-manipulator` для сжатия изображений до приемлемого разрешения (например, max 1280px по ширине, quality 0.8) перед отправкой на сервер.

## 3. High Priority Improvements (Высокий приоритет / P1)

### Issue 3.1: Отсутствие проверки активной подписки у исполнителя при отклике на заказ
*   **Файл**: `backend/src/modules/orders/orders.service.ts` (метод `apply()`)
*   **Причина**: В системе разработан качественный модуль подписок `SubscriptionModule` с проверкой `checkActiveSubscription(userId)`. Однако в методе `apply` бэкенда, отвечающем за отклик мастера на заказ, данная проверка полностью отсутствует.
*   **Последствия**: Мастера могут беспрепятственно и бесплатно откликаться на неограниченное количество заказов, полностью обходя монетизацию платформы. Это делает бизнес-модель нефункционирующей.
*   **Решение**: Внедрить вызов `SubscriptionService` в метод `apply` класса `OrdersService`:
    ```typescript
    const hasSubscription = await this.subscriptionService.checkActiveSubscription(executorId);
    if (!hasSubscription) {
        throw new ForbiddenException('Для отклика на заказ требуется активная подписка');
    }
    ```

### Issue 3.2: Отсутствие механизма JWT Refresh Tokens (Сессия внезапно прерывается)
*   **Файлы**: `backend/src/modules/auth/auth.service.ts`, `src/services/ApiService.ts`
*   **Причина**: Бэкенд генерирует JWT-токен авторизации с фиксированным временем жизни. Механизм обновления токенов (Refresh Token / sliding session) отсутствует.
*   **Последствия**: Пользователь (мастер или заказчик) будет внезапно разлогинен прямо посреди рабочего процесса (например, во время заполнения деталей заказа или переписки в чате), как только истечет срок жизни Access токена. Это критически ухудшает пользовательский опыт (UX).
*   **Решение**:
    1. Внедрить выпуск пары токенов `access_token` (expiresIn: '15m') и `refresh_token` (expiresIn: '7d') при авторизации.
    2. На клиенте хранить `refresh_token` в `expo-secure-store` и настроить Axios Interceptor в `ApiService.ts` на автоматический перехват ошибки `401 Unauthorized` для бесшовного обновления сессии.

### Issue 3.3: Безопасность режима OTP-авторизации в продакшене (OTP Leak Block)
*   **Файл**: `backend/src/modules/auth/auth.service.ts`
*   **Причина**: В коде авторизации жестко зашит демонстрационный режим (`AUTH_MODE=development`), при котором бэкенд возвращает код `1234` прямо в ответе API на запрос OTP.
*   **Последствия**: Любой злоумышленник, зная номер телефона любого пользователя (включая администраторов), сможет мгновенно войти в их аккаунты, просто запросив код и введя `1234`.
*   **Решение**:
    1. На бэкенде перед релизом гарантировать установку переменной окружения `AUTH_MODE=production`.
    2. Интегрировать SMS-шлюз (SMS.ru, Twilio, SigmaSMS) в `AuthService.requestOtp` для генерации случайного 4-значного числа и его отправки по реальной сети связи.

## 4. Medium Priority Improvements (Средний приоритет / P2)

### Issue 4.1: Отсутствие пагинации в эндпоинтах получения списков
*   **Файлы**: `backend/src/modules/orders/orders.controller.ts`, `backend/src/modules/chats/chats.controller.ts`, `backend/src/modules/reviews/reviews.controller.ts`
*   **Причина**: Все эндпоинты, возвращающие списки заказов, сообщений или отзывов, делают полную выборку из базы данных без ограничений по объему (`take`, `skip`, `cursor`).
*   **Последствия**: При росте базы данных до 1000+ заказов или длинных переписках в чатах запросы будут возвращать мегабайтные JSON-ответы. Это приведет к медленной отрисовке списков на мобильных устройствах, фризам прокрутки `FlatList` и высокому потреблению оперативной памяти.
*   **Решение**:
    1. Внедрить курсорную пагинацию (Cursor-based) для загрузки сообщений чата (по `createdAt` или `id`).
    2. Внедрить офсетную пагинацию (`page`, `limit`) для списков заказов и отзывов.

### Issue 4.2: Раскрытие внутренних ошибок базы данных клиенту (Prisma Exception Leak)
*   **Файл**: `backend/src/main.ts`
*   **Причина**: Отсутствует глобальный фильтр исключений для Prisma ORM. Ошибки базы данных (например, ошибки ограничений уникальности, типов полей) в сыром виде возвращаются в ответе сервера.
*   **Последствия**: Утечка внутренней структуры таблиц и типов данных базы данных, что упрощает злоумышленникам проведение целевых атак на инфраструктуру бэкенда.
*   **Решение**: Создать и подключить в `main.ts` глобальный фильтр `PrismaClientExceptionFilter`, который перехватывает ошибки Prisma и преобразует их в стандартизированные ответы:
    ```typescript
    // P2002 (Unique constraint) -> 409 Conflict
    // P2025 (Record not found) -> 404 Not Found
    ```

### Issue 4.3: Отсутствие оффлайн-очереди запросов (Offline Mutation Queue)
*   **Файлы**: `src/services/RequestRouter.ts`, `src/services/ApiService.ts`
*   **Причина**: Мобильный клиент имеет встроенные механизмы дедупликации кэша, но не поддерживает буферизацию действий, совершенных в условиях полной потери сети (например, оффлайн-отправка сообщений или локальное создание заказа).
*   **Последствия**: При потере сети запрос сразу возвращает ошибку, блокируя интерфейс. Пользователь должен вручную дожидаться появления сети и отправлять запрос повторно.
*   **Решение**: Интегрировать библиотеку `@react-native-community/netinfo`. При потере сети складывать критические POST/PATCH/DELETE запросы в оффлайн-очередь в MMKV-хранилище и автоматически выполнять их (Reconciliation) при возвращении стабильного интернет-соединения.

## 5. Low Priority Improvements (Низкий приоритет / P3)

### Issue 5.1: Отсутствие составного index-фильтра для сортировки мастеров по рейтингу
*   **Файл**: `backend/prisma/schema.prisma`
*   **Причина**: В модели `User` индексы на `role` и `rating` объявлены как два отдельных индекса.
*   **Последствия**: При поиске лучших мастеров (сортировка по `rating DESC` среди пользователей с ролью `WORKER`) СУБД PostgreSQL не сможет эффективно использовать оба индекса одновременно, что вызовет сканирование таблиц (Table Scan) при больших объемах данных.
*   **Решение**: Добавить в модель `User` составной индекс `@@index([role, rating(sort: Desc)])`.

### Issue 5.2: Статическое форматирование дат без учета локали
*   **Файл**: `src/utils/date.ts`
*   **Причина**: Для форматирования дат используются встроенные методы JavaScript, которые зависят от настроек операционной системы смартфона.
*   **Последствия**: Разнородное отображение дат у пользователей (например, "Feb 23, 2025" вместо "23 февраля 2025 г.").
*   **Решение**: Зафиксировать русскую локализацию с помощью пакета `date-fns` и импортировать локаль `ru`.

## 6. Performance Report (Анализ производительности)

1.  **Map Engine (Отлично)**: Оптимизирован благодаря радиусу в 100 км на бэкенде (`SYNC_RADIUS = 100`) и 300-миллисекундному дебаунсу. Карта не "спамит" бэкенд запросами при каждом микродвижении пальца пользователя.
2.  **FlatList (Зона риска)**: В экранах `OrdersListScreen` и `ChatListScreen` списки отрисовывают тяжелые карточки без оптимизационных пропсов. Требуется настроить:
    - `initialNumToRender={10}`
    - `maxToRenderPerBatch={10}`
    - `windowSize={5}`
    - `removeClippedSubviews={Platform.OS === 'android'}`
3.  **Лишние ре-рендеры (Устранено)**: Экраны списков и маркеры карты были успешно защищены с помощью уникальных составных ключей вида `${item.id}_${item.status}`. Это гарантирует, что маркер или карточка обновляются только тогда, когда WebSocket-событие действительно изменило статус заказа, не вызывая перерисовку всей карты.

## 7. Security Report (Аудит безопасности)

1.  **Токены авторизации (Отлично)**: Токены сохраняются в защищенном хранилище `expo-secure-store`, обеспечивающем шифрование Keychain (на iOS) и Keystore (на Android).
2.  **Google Maps API Keys**: Ключи зашиты в конфигурационных файлах. Крайне важно ограничить действие API-ключей в Google Cloud Console по SHA-1 отпечатку сертификата подписи (для Android) и Bundle ID (для iOS). Это исключит использование ваших ключей третьими лицами в случае утечки исходного кода.
3.  **Защита API от спама**: В приложении отсутствует защита от подбора OTP-кодов и спама запросами (SMS Bomber). На бэкенде необходимо установить лимит запросов на эндпоинт `/auth/request-otp` с одного IP/телефона в минуту с помощью пакета `@nestjs/throttler`.

## 10. Business Flow Audit (Анализ бизнес-сценариев маркетплейса)

Даже технически совершенное приложение может потерпеть неудачу на рынке из-за логических и сценариарных тупиков в пользовательских путях (User Journeys). Ниже представлен подробный анализ жизненного цикла заказов и взаимодействий между **Заказчиком (Employer)** и **Мастером (Worker)**.

---

### 👤 Сценарий А: Путь Заказчика (Employer Journey)

```
Регистрация/Вход (OTP)
     ↓
Создание заказа (Title, Адрес, Координаты, Описание, Бюджет)
     ↓
Публикация (Автоматический статус PUBLISHED)
     ↓
Получение откликов (Смена статуса на HAS_RESPONSES)
     ↓
Выбор мастера (Принятие заявки, статус CLAIMED, автосоздание Чата, автоотклонение остальных)
     ↓
Общение в Чате (Согласование деталей, переход в статус IN_PROGRESS)
     ↓
Завершение работы (Мастер нажимает "Завершить", статус COMPLETED)
     ↓
Взаимный Отзыв (Оценка мастера, пересчет рейтинга)
```

#### 🔍 Ответы на критические вопросы по пути Заказчика:

#### 1. Может ли зависнуть заказ в системе?
**Да, в текущей логике существует два сценария "вечного зависания":**
*   **Сценарий зависания №1 (Мастер пропал до начала работ)**: Заказчик выбрал мастера (статус `CLAIMED`), но мастер передумал, не нажимает кнопку "Начать работу" (`startWork`) и перестал отвечать на звонки/сообщения. В текущем коде `canTransition` бэкенда **запрещает** заказчику отменить выбор исполнителя или вернуть заказ обратно в поиск (из `CLAIMED` можно перейти только в `IN_PROGRESS` или `CANCELLED`). Кнопка отмены для заказчика в UI блокируется, и заказ зависает.
*   **Сценарий зависания №2 (Мастер пропал в процессе выполнения)**: Мастер нажал кнопку "Начать работу" (статус `IN_PROGRESS`), выполнил часть работ плохо, бросил объект и ушел. Заказ навсегда заблокирован в статусе `IN_PROGRESS`. Заказчик не может его отменить (отмена из `IN_PROGRESS` заблокирована на бэкенде для защиты мастеров) и не может завершить его самостоятельно.
*   **Решение**:
    1.  **Арбитраж (Dispute)**: Внедрить полноценный статус `DISPUTE`. Добавить в UI кнопку "Открыть спор" для обеих сторон, которая переводит заказ в статус спора, приостанавливает автопереходы и уведомляет администратора маркетплейса через панель управления для ручного решения.
    2.  **Авто-отмена по тайм-ауту (SLA)**: Если в течение 12-24 часов после запланированной даты проведения работ в статусе `CLAIMED` мастер не нажал кнопку "Начать работу", заказ должен автоматически возвращаться в статус `PUBLISHED` со снятием брони мастера и штрафом к рейтингу исполнителя за срыв SLA.

#### 2. Что если мастер отказался от работы?
*   **До выбора мастера (статус PENDING)**: Мастер может в любой момент отозвать свой отклик через `cancelApplication` на клиенте. Бэкенд выполняет это безопасно. Если это был последний отклик, бэкенд автоматически возвращает статус заказа из `HAS_RESPONSES` в `PUBLISHED`. Всё работает корректно.
*   **После выбора мастера (статус CLAIMED)**: В кодовой базе бэкенда **полностью отсутствует эндпоинт для отказа мастера от уже принятого заказа**. Если мастер понимает, что не может выполнить работу, он не имеет технической возможности отказаться через приложение. Заказчик также заблокирован.
*   **Решение**: Добавить эндпоинт `POST /orders/:id/reject-assigned` для мастеров. Метод должен:
    1.  Сбрасывать `executorId` в `null`.
    2.  Переводить статус заказа обратно в `HAS_RESPONSES` (или `PUBLISHED`).
    3.  Переводить заявку отказавшегося мастера в статус `REJECTED` (чтобы он не мог откликнуться повторно).
    4.  Применять автоматический штраф к рейтингу мастера (например, -0.2 звезды) за отказ от принятых обязательств для борьбы с безответственностью.

#### 3. Что если заказчик создал заказ и пропал (не отвечает)?
*   Если заказчик опубликовал заказ, получил отклики от мастеров, но передумал делать ремонт и просто забросил приложение: мастера видят заказ в статусе `HAS_RESPONSES` и "замораживают" свое рабочее время под эту дату в календаре, надеясь на сделку.
*   **Решение**: Внедрить автоархивацию / срок жизни (TTL) заказа. Написать фоновую задачу (Cron-job), которая ежедневно проверяет заказы в статусах `PUBLISHED`/`HAS_RESPONSES`. Если дата запланированных работ наступила или прошла, а исполнитель не был выбран, заказ автоматически переводится в статус `CANCELLED` или специальный архивный статус `EXPIRED` (Истёк).

#### 4. Что если два мастера будут выбраны одновременно (Гонка данных)?
*   **Технический разбор**: Этот сценарий **надежно и идеально защищен** на уровне бэкенда.
    - Выбор исполнителя в методе `OrdersService.acceptApplication` выполняется внутри атомарной транзакции СУБД `$transaction`.
    - Первая транзакция, обработанная PostgreSQL, обновляет статус заказа на `CLAIMED` и прописывает `executorId`.
    - В этой же транзакции все остальные отклики (`Application`) по данному `orderId` принудительно переводятся в статус `REJECTED`.
    - Вторая параллельная транзакция при обработке встретит проверку статуса заказа:
      ```typescript
      if (app.order.status !== OrderStatus.HAS_RESPONSES && app.order.status !== OrderStatus.PUBLISHED) {
          throw new ConflictException(`Cannot accept application. Order status is already ${app.order.status}`);
      }
      ```
      Поскольку статус уже стал `CLAIMED`, бэкенд мгновенно выбросит ошибку `ConflictException (код 409)`. Второй мастер не сможет быть выбран ни при каких обстоятельствах.
*   **Решение на клиенте**: На мобильном клиенте необходимо перехватывать HTTP-код `409` при нажатии кнопки "Принять исполнителя" и выводить дружелюбное всплывающее окно: *"Извините, этот заказ уже укомплектован исполнителем или статус заказа изменился. Пожалуйста, обновите страницу."*

#### 5. Что если статус поменяли в обход UI напрямую через API (взлом/манипуляция)?
*   Если злоумышленник попытается отправить `PATCH /orders/:id` с телом `{"status": "PUBLISHED"}` для заказа, который уже находится в процессе работы (`IN_PROGRESS`), бэкенд защищен:
    - Метод `update` проверяет права владения (`order.employerId === userId`).
    - Метод использует внутреннюю функцию валидации `canTransition(from, to)`.
    - Правила `canTransition` строго запрещают движение назад по цепочке состояний:
      ```typescript
      // Из IN_PROGRESS нельзя вернуться в PUBLISHED/CLAIMED
      return priorities[to] > priorities[from];
      ```
    - Таким образом, бэкенд выбросит `409 Conflict` при любой попытке нарушить логику переходов состояний через API. Защита работает на 100%.

#### 🔍 Анализ пограничных сценариев и зон риска пути Мастера:

#### 1. Оплата работы и отсутствие Безопасной Сделки (Escrow) — Главный бизнес-риск маркетплейса
*   **Проблема**: В текущей версии системы полностью отсутствует финансовый шлюз. Предполагается, что заказчик рассчитывается с мастером наличными или прямым переводом на карту (p2p) по факту завершения работ. Средний чек на монтаж потолков высок (от 15 000 до 100 000+ рублей).
*   **Бизнес-риск**: Мастер выполняет тяжелую физическую работу, тратит дорогие расходные материалы, нажимает кнопку "Завершить работу" (`completeWork`), но недобросовестный заказчик отказывается платить или скрывается. Мастер полностью беззащитен, платформа не имеет рычагов воздействия. Это приведет к массовому оттоку мастеров и судебным рискам для платформы.
*   **Решение (Внедрение Escrow/Безопасной сделки)**:
    1.  Интегрировать платежный интернет-эквайринг (например, ЮKassa, Tinkoff API или Stripe) для холдирования средств.
    2.  При одобрении заявки мастера заказчик должен внести 100% предоплату (или стоимость материалов). Сумма "замораживается" (холдируется) на транзитном счете платформы.
    3.  После того как мастер нажимает "Завершить работу", а заказчик подтверждает выполнение в UI, деньги автоматически размораживаются и переводятся на расчетный счет/карту мастера за вычетом комиссии платформы.
    4.  В случае споров средства остаются заблокированными до вынесения решения арбитражем маркетплейса.

#### 2. Фильтрация заказов по специализации (Карта)
*   **Проблема**: На карте `MapScreen` мастер видит абсолютно все заказы подряд. Но мастера делятся по узким специализациям: замерщики (`FROZE`), монтажники сложных конструкций (`INSTALLATION`), специалисты по ремонту полотен (`REPAIR`). Мастеру приходится вручную прокликивать десятки маркеров на карте, чтобы найти подходящую работу.
*   **Решение**: Внедрить фильтрацию по типу работ (`workType` Enum) в верхнюю панель фильтров `MapScreen` на мобильном клиенте. Передавать выбранный тип работы в метод `getOrdersSpatial` для сужения выборки на уровне БД.

#### 3. Защита от накрутки рейтинга (Mutual Reviews Integrity)
*   **Проблема**: Мастера могут создавать фейковые аккаунты заказчиков, размещать копеечные заказы, моментально принимать самих себя, нажимать "Завершить работу" и оставлять себе отзывы с оценкой 5.0, искусственно завышая свой рейтинг и накручивая счетчик `completedOrders`.
*   **Решение**:
    1.  **Проверка гео-позиции**: Использовать `expo-location` для сверки координат мастера при нажатии "Начать работу" и "Завершить работу" с координатами заказа на карте. Если мастер не находился на объекте в указанные даты, блокировать переход статусов или помечать сделку как "подозрительную".
    2.  **Анти-фрод по устройствам**: Привязывать сессии к уникальному ID устройства (UUID девайса), чтобы блокировать сделки между работодателем и мастером, если они запущены на одном физическом телефоне.
    3.  **Платный отклик**: Подписочная модель или комиссия за отклик уже усложняют накрутку, так как за каждый фейковый заказ мошеннику придется платить реальные деньги платформе.
