# ТЕХНИЧЕСКИЙ АУДИТ ФРОНТЕНДА (REACT NATIVE / EXPO) — СТО ОТЧЕТ

Этот отчет содержит глубокий технический анализ клиентской части приложения **CeilingsApp**. Анализ сфокусирован на архитектуре, производительности, стабильности сетевого слоя (API, WebSockets), работе с кэшем/стейтом, безопасности и потенциальных "минах замедленного действия", которые могут привести к падению приложения при масштабировании бизнеса.

---

## 1. РЕЗЮМЕ ДЛЯ БИЗНЕСА (EXECUTIVE SUMMARY)

Приложение спроектировано как современная платформа для заказа услуг по монтажу потолков с интерактивной картой и чатами в реальном времени. С точки зрения UX и базовой идеи, продукт выглядит отлично: есть гео-фильтрация, "умный" парсинг заказов, кэширование и поддержка оффлайн-режима.

Тем не менее, под капотом скрывается ряд **серьезных архитектурных компромиссов (technical debt)**, которые:
1. **Увеличивают стоимость разработки:** Стандартные инструменты (Zustand, React Query) внедрены частично, но ключевая бизнес-логика написана на кастомных "велосипедах" (ручной стейт-менеджер `EntityStore`, самописный роутер запросов `RequestRouter`). Это замедлит онбординг новых разработчиков.
2. **Угрожают стабильности при росте нагрузки:** Присутствуют неоптимальные алгоритмы работы с картой и гео-запросами (отсутствие дебаунсинга при вводе адреса, частые тяжелые перезапросы данных при переподключении сокетов). При росте базы пользователей до 5 000+ MAU сервера начнут испытывать перегрузки, а пользователи — зависания интерфейса.
3. **Несут риски сбоев на слабых устройствах:** Отсутствие оптимизации изображений и утечки памяти в подписках могут приводить к вылетам приложения на бюджетных Android-смартфонах.

## 2. АРХИТЕКТУРНЫЙ АНАЛИЗ И СТРУКТУРА КОДА

### 2.1. "Мертвый груз" стейт-менеджмента (Zustand vs Кастомный Стор)
В проекте установлена отличная библиотека `zustand` и созданы файлы сторов:
* `src/store/orders.store.ts`
* `src/store/chat.store.ts`
* `src/store/auth.store.ts`

**Проблема:** Они практически **не используются**. Вся работа со стейтом заказов, пользователей и кэшированием перенесена в кастомный класс `EntityStore.ts` и `MapEngine.ts`.
* `EntityStore` работает на ручных подписках (`MapEngine.subscribe`) с ручным вызовом обновлений через `triggerNotify`.
* Это вынуждает разработчиков писать код вида `setDisplayedOrders([...newOrders])` внутри `useEffect` на экранах (например, в `MapScreen.tsx`).

**Критичность: Medium (P2)**
**Последствия:**
* Отсутствие реактивности "из коробки". Если обновится один заказ, перерендерится вся карта или весь список, так как нет мемоизации на уровне селекторов стейта.
* Высокий риск утечек памяти, если разработчик забудет вызвать `unsubscribe()` при размонтировании сложного компонента.
* Дублирование концепций (в проекте одновременно сосуществуют Zustand, Context API и кастомный EntityStore).

## 3. КРИТИЧЕСКИЕ ОШИБКИ И УЯЗВИМОСТИ (P0 - P2)

### P0: Отсутствие дебаунсинга геокодинга (DDoS самого себя и блокировка API)
**Где живет:** `src/screens/CreateOrderScreen.tsx`, метод `handleAddressChange`.

**Что происходит:** При вводе адреса в поле создания заказа приложение выполняет геокодинг (`Location.geocodeAsync`) и обратный геокодинг (`Location.reverseGeocodeAsync`) **на каждый введенный символ**, начиная с длины строки > 2.
```typescript
const handleAddressChange = async (text: string) => {
  setForm({ ...form, address: text });
  if (text.length > 2) {
     // Сразу летят тяжелые асинхронные запросы без задержки!
     const results = await Location.geocodeAsync(...);
  }
}
```
Если пользователь быстро вводит адрес "Москва, улица Ленина, дом 15" (28 символов), приложение отправит **26 параллельных запросов** к системным службам геолокации Apple/Google или сторонним API.

**Последствия:**
* Операционная система девайса или провайдер API (например, Google/Yandex/Expo) мгновенно заблокируют приложение за превышение лимитов (Rate Limit / Throttling).
* Интерфейс будет жутко лагать на мобильных устройствах из-за перегрузки асинхронного моста (Bridge) между JS и Native-кодом.
* Всплывающие подсказки (suggestions) будут отображаться хаотично из-за race conditions (ответ на более короткий запрос придет позже ответа на длинный запрос).

### P1: Риск падения сервера при переподключениях WebSocket (Reconnect Storm)
**Где живет:** `src/services/SocketService.ts`, событие сокета `reconnect`.

**Что происходит:** На мобильных устройствах сокет-соединение рвется постоянно (при переходе с Wi-Fi на LTE, в лифтах, туннелях). В `SocketService` настроено автоматическое восстановление:
```typescript
this.socket.io.on('reconnect', async () => {
  ...
  // При каждом реконнекте насильно дергается полная перезагрузка карты с сервера
  await mapEngine.initialLoad(region.latitude, region.longitude);
});
```
**Последствия:**
Если у вас 10 000 активных пользователей, и в метро временно пропала связь, при восстановлении сети все 10 000 девайсов **одновременно** отправят тяжелые пространственные POST/GET-запросы к API для перезагрузки карты. Это классическая проблема "шторма переподключений" (Reconnect Storm), которая положит бэкенд-сервер.
*Решение:* Использовать инкрементальное обновление (синхронизацию только изменившихся объектов по timestamp) вместо полной перезагрузки, а также добавить случайную задержку (jitter) перед отправкой запроса.

### P1: Жесткие географические ограничения (Зависание бизнеса в МСК)
**Где живет:** `src/screens/CreateOrderScreen.tsx`, метод `handleGeocode`.

**Что происходит:** В коде жестко зашиты координаты Московского региона для валидации геокодинга:
```typescript
if (res.latitude > 54 && res.latitude < 57 && res.longitude > 35 && res.longitude < 40) {
  bestResult = res;
  break;
}
```
**Последствия:**
Если вы решите запустить сервис в Санкт-Петербурге, Новосибирске, Краснодаре или любой другой точке за пределами Московской области, приложение будет молча игнорировать геокодирование адресов. Заказчики не смогут создать заказы, так как маркер на карте просто не появится, а приложение не выдаст понятной ошибки. Это блокирует любое масштабирование бизнеса.

---

### P2: Потенциальный сбой Socket URL при смене домена
**Где живет:** `src/services/SocketService.ts`, метод `connect()`.

**Что происходит:** Извлечение WebSocket URL из API URL сделано через простую замену строки:
```typescript
const socketUrl = url.replace('/api/', '');
```
**Последствия:**
Если в будущем ваш API-адрес изменится (например, станет `https://ceilingsapp.com/api/v1/` или `https://api.v2.ceilings.com/`), замена `/api/` сломает URL веб-сокетов, сделав его некорректным (например, останется `https://ceilingsapp.com/v1/` вместо чистого хоста). Подключение сокетов тихо упадет, и чаты с интерактивной картой перестанут работать.

---

### P2: Отсутствие полноценного сжатия изображений при загрузке
**Где живет:** `src/screens/CreateOrderScreen.tsx`, метод `pickImage`.

**Что происходит:** Фотографии выбираются через `ImagePicker.launchImageLibraryAsync` с параметром `quality: 0.7`.
**Последствия:**
Камера современного смартфона делает снимки объемом от 4 до 12 МБ с разрешением 4000x3000px. Параметр `quality: 0.7` немного сжимает JPEG-артефакты, но разрешение остается огромным. Загрузка 3-5 таких фотографий в виде массива строк в бэкенд на медленном 3G-интернете гарантированно завершится таймаутом сетевого запроса или вызовет Out-Of-Memory краш приложения на стороне клиента.
*Решение:* Использовать `expo-image-manipulator` для принудительного ресайза изображений до разумного максимума (например, 1280x960px) перед отправкой.

## 4. ОШИБКИ И ЗАМЕЧАНИЯ ПО UI/UX И ОТКАЗОУСТОЙЧИВОСТИ

### 4.1. Риск бесконечного лоадера при сетевых сбоях
На экранах `MapScreen.tsx` и `OrdersListScreen.tsx` индикаторы загрузки завязаны на флаги стейта. Если бэкенд вернет ошибку, которая не перехвачена должным образом, или запрос "зависнет" на уровне провайдера сети, пользователь останется смотреть на бесконечно крутящийся ActivityIndicator без возможности обновить страницу вручную.

### 4.2. Дублирование кода логики подписок
Код подписок на обновления в `MapScreen` и `OrdersListScreen` дублирует логику:
* Используется `isSubscribedRef` для предотвращения двойной подписки (костыль из-за особенностей StrictMode в React 18/19).
* В идеале это должно решаться через кастомный хук или интеграцию `react-query` (который уже объявлен в бэклоге, но не внедрен полностью во всех экранах).

## 5. ПОЛОЖИТЕЛЬНЫЕ СТОРОНЫ (ЧТО СДЕЛАННО ОТЛИЧНО)

Несмотря на критику, проект имеет сильный фундамент:
1. **Синхронное хранилище (MMKV):** Отказ от медленного асинхронного `AsyncStorage` в пользу `react-native-mmkv` — это топ-решение. Оно обеспечивает моментальную инициализацию приложения без лагов на старте.
2. **Логирование и Трейсинг (`LoggerService`):** Внедрена отличная сквозная система логирования сетевых запросов, ошибок и переходов состояний. Это сильно упрощает отладку в продакшене.
3. **Парсинг заказов (`parseOrderText`):** Наличие ИИ/эвристического парсинга текста заказа прямо на фронтенде — мощнейшая фича, которая сильно поднимает конверсию (заказчику проще скопировать текст из Telegram/WhatsApp, чем заполнять форму).
4. **Защита от двойных транзакций:** Использование `idempotencyKey` на экранах отклика и создания заказа предотвращает случайное создание дубликатов при плохой связи.

## 6. ПОШАГОВЫЙ ПЛАН УЛУЧШЕНИЙ (СТРАТЕГИЯ СТО)

Для вывода продукта на уровень надежного Enterprise-решения предлагаю следующий план работ, разбитый по приоритетам:

### Фаза 1: Срочные исправления (P0 - P1) — Срок: 1-2 недели
1. **Внедрить дебаунсинг (Debounce) на ввод адреса:**
   Добавить задержку в 500-800 мс перед вызовом геокодинга в `CreateOrderScreen.tsx`, чтобы запросы не улетали на каждую букву.
2. **Исправить географическое ограничение:**
   Убрать жестко зашитые координаты Московской области из `CreateOrderScreen.tsx` или сделать их динамическими (в зависимости от текущего региона на карте).
3. **Оптимизировать частоту реконнектов сокетов:**
   Добавить экспоненциальный бэк-офф (exponential backoff with jitter) для WebSocket-подключений и убрать тяжелый `mapEngine.initialLoad()` при каждом кратковременном обрыве.

### Фаза 2: Оптимизация и UX (P2) — Срок: 2-3 недели
1. **Внедрить ресайз картинок (`expo-image-manipulator`):**
   Сжимать загружаемые фотографии до разрешения 1280px по широкой стороне и качества 0.8 перед отправкой на сервер.
2. **Убрать ручной стейт-менеджмент на экранах:**
   Полноценно переписать реактивную часть (списки заказов, профиль) на полноценный Zustand стор или связку React Query + Zustand. Избавиться от ручных подписок `useEffect` с `[...newOrders]`.
3. **Безопасный парсинг WebSocket URL:**
   Использовать надежный парсер URL (например, встроенный класс `URL` в JS) для конструирования адреса сокетов, вместо хрупкого `.replace()`.

### Фаза 3: Масштабирование и надежность (P3) — Срок: В процессе развития
1. **Покрытие тестами:**
   Настроить правильный Babel-транспилятор для Jest (исправить ошибку `Cannot find module 'babel-preset-expo'`) и покрыть интеграционными тестами ключевые сценарии: авторизация, создание заказа, отправка сообщений.
2. **Оффлайн-режим (Offline-first):**
   Полностью реализовать очередь отложенных действий (Pending Action Queue) для оффлайн-режима, чтобы заказчик мог составить заказ в подвале (без интернета), а приложение само отправило его при выходе на связь.

---

### Заключение СТО:
Фронтенд имеет огромный потенциал и написан разработчиками с хорошим пониманием мобильной специфики (о чем говорит выбор MMKV и архитектура логгера). Однако спешка перед релизом привела к накоплению критических багов (Rate-limiting геокодинга, Reconnect Storm сокетов).

Реализация первого этапа исправлений займет не более недели, но сделает систему **в 10 раз стабильнее** под нагрузкой.
