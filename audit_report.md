# Отчет по аудиту проекта Ceilingsapp

## 1. Конфликты зависимостей и конфигурация
- **React 19 и React Native 0.81:** Проект использует самые свежие версии, что похвально, но `@testing-library/react-native` и `react-test-renderer` ожидают React 18. Это вызывает ошибки при `npm install`.
- **Firebase SDK:** Используется `firebase/compat`, который является устаревшим способом работы с Firebase в веб/JS средах. Рекомендуется переход на модульный SDK (v9+), что уменьшит размер бандла и улучшит типизацию.
- **AsyncStorage:** Firebase Auth выдает предупреждение о несоответствии версии peer dependency для `@react-native-async-storage/async-storage`.

**Рекомендации:**
- Использовать `--legacy-peer-deps` при установке или дождаться обновления тестовых библиотек до поддержки React 19.
- Рассмотреть переход на модульный Firebase SDK.

## 2. Проблемы в логике и коде
- **Inconsistent Order Statuses:** В `types/index.ts` и коде используются разные наборы статусов (`pending`, `new`, `accepted`, `in_work`, `executing`, `in_progress`, `started`). Это может привести к багам, когда заказ "зависает" из-за того, что UI ожидает один статус, а в базе лежит другой.
- **OrderService.ts:**
    - В методе `createOrder` используется `JSON.parse(JSON.stringify(...))` для глубокой очистки данных. Это "костыльный" метод, который может удалять объекты `Date` или `FieldValue`.
    - Метод `uploadImage` через `fetch(uri).blob()` может быть нестабилен на некоторых версиях Android.
- **MapScreen.tsx:**
    - Вычисление дистанции для всех заказов происходит внутри `useMemo`. При большом количестве заказов (>1000) это может привести к подтормаживанию UI при скролле или перемещении карты.
    - В `onMarkerPress` делается запрос в Firestore для получения профиля заказчика. Это хорошо, но нет кэширования профилей.
- **CreateOrderScreen.tsx:**
    - Логика геокодирования (поиск координат по адресу) довольно сложная и делает несколько последовательных запросов. Это может работать медленно при плохом интернете.

**Рекомендации:**
- Унифицировать `OrderStatus` и использовать его строго через `enum` или `const union type`.
- Оптимизировать `MapScreen`, добавив кэширование или ограничив количество одновременно обрабатываемых заказов.
- Добавить валидацию форм (например, через `yup` или `zod`).

## 3. Безопасность и Правила (Firebase Rules)
- **Firestore Rules:**
    - Правило для чтения профиля пользователя (`/users/{userId}`) разрешает чтение, если существует хоть один заказ в коллекции `orders`. Это слишком широкое правило, которое потенциально позволяет любому пользователю увидеть телефон другого, если он знает, как отправить запрос.
    - `isSubscribed()` делает `get()` запрос к профилю пользователя при каждой проверке правил. Это может увеличить количество платных операций чтения (хотя Firestore кэширует такие запросы в рамках одного запроса).
- **Скрытие данных:** Хотя есть утилита `maskPhoneNumbers`, она не применяется повсеместно (например, в заголовках заказов или деталях, если разработчик забыл ее вызвать).

**Рекомендации:**
- Вынести телефонные номера в отдельную подколлекцию (например, `users/{userId}/private/data`), к которой будет доступ только у владельца или подтвержденного исполнителя.
- Усилить правила Firestore, проверяя конкретную связь между пользователем и заказом.

## 4. UI/UX и прочее
- **Push Notifications:** В `NotificationService.ts` жестко прописан `projectId`. При смене аккаунта Expo это перестанет работать.
- **i18n:** Использование `i18n-js` версии 4+ — хороший выбор, но стоит убедиться, что все строки вынесены в переводы (сейчас часть текста в `MapScreen` захардкожена на русском).

## Итог
Проект находится в хорошем состоянии с точки зрения структуры, но требует "причесывания" зависимостей и унификации логики статусов заказов. Самым критичным моментом является потенциальная утечка персональных данных через слишком открытые правила Firestore.
