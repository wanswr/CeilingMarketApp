# Архитектурный аудит Backend части CeilingMarketApp

## 1. Общая оценка
Архитектура проекта спроектирована грамотно с соблюдением принципа централизации вокруг сущности **User**. Система связей в базе данных позволяет масштабировать проект без радикального изменения схемы.

---

## 2. Что уже сделано правильно
- **Централизация User**: Все ключевые данные (заказы, отклики, чаты, отзывы) привязаны к ID пользователя.
- **Взаимные отзывы**: Реализована современная модель (unique на пару заказ+автор), позволяющая обеим сторонам оценивать друг друга.
- **Безопасность**: Применение `JwtAuthGuard` и проверка владения ресурсом (Ownership) в критических местах.
- **Целостность данных**: Правильно настроенные `onDelete: Cascade` для чатов и заказов предотвращают накопление мусора в БД.
- **Гео-индексация**: Наличие композитных индексов в модели `Order` обеспечивает быструю работу карты.

---

## 3. Выявленные проблемы и риски
1. **[Критично] Отсутствие проверки подписки**: Метод `OrdersService.apply` не проверяет наличие активной подписки у исполнителя, хотя логика проверки в `SubscriptionService` существует. Это позволяет мастерам откликаться бесплатно.
2. **[Желательно] Отсутствие моделей расширения**: Нет таблиц для `Portfolio` и `Notification`, что приведет к хранению этих данных в неструктурированном виде (например, просто массив строк в User), если не исправить сейчас.
3. **[Средне] Типизация API**: В `OrdersController` параметры запроса (`Query`) приходят как строки, и их преобразование в числа происходит вручную. Это может привести к ошибкам `NaN` при некорректных запросах.
4. **[Низко] Нагрузка на User**: Отсутствуют индексы на поля `User.rating` и `User.role`. При росте базы до тысяч пользователей сортировка исполнителей по рейтингу станет медленной.

## 4. Рекомендации по изменению Prisma Schema

### Добавить связи и таблицы:
- **PortfolioItem**: Создать отдельную таблицу, связанную с User, для хранения фото работ, описаний и категорий.
- **Notification**: Таблица для хранения истории push-уведомлений.
- **WorkType (Entity)**: Сейчас это Enum. Для будущего расширения (сотни видов работ) лучше перевести в отдельную таблицу `Category`.

### Добавить индексы:
```prisma
model User {
  // ...
  @@index([role, rating(sort: Desc)]) // Для быстрого поиска топовых мастеров
}
```

## 5. Рекомендации по API
- **Унификация ответов**: Привести все эндпоинты к единому стандарту `{ success: boolean, data: any, error?: string }`.
- **Pre-fetch данных**: Добавить эндпоинт `GET /users/me/dashboard`, который одним запросом возвращает профиль, количество активных заказов и статус подписки.
