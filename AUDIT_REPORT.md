# Технический аудит проекта CeilingsApp (V2)

## 1. Executive Summary (CTO-level)

**CeilingsApp** — специализированный Uber-like маркетплейс для сферы натяжных потолков. Стек: **React Native (Expo)** + **NestJS (Prisma/PostgreSQL)**.

**Вердикт:** Архитектура проекта на высоком уровне (особенно MapEngine), но требует доводки «последней мили» для production. Текущие риски связаны с отсутствием полноценного медиа-сервиса, юридическим комплаенсом (152-ФЗ) и жестко зашитыми ролевыми ограничениями.

---

## 2. Архитектурная оценка

### Сильные стороны (Pros)
1.  **MapEngine**: Грамотное разделение на вьюпорт (`MapViewportStore`) и данные (`EntityStore`). Использование локальной сетки для фильтрации — уровень топовых сервисов.
2.  **Нормализация**: Данные на фронте хранятся в Map/Record, что исключает дублирование при обновлении через WebSockets.
3.  **NestJS Модульность**: Чистое разделение ответственности на бэкенде.

### Слабые стороны (Cons)
1.  **Ролевой дуализм**: Отсутствие гибкого переключения между ролями Заказчик/Исполнитель без потери контекста.
2.  **Медиа-инфраструктура**: Изображения хранятся как заглушки в БД, нет реального пайплайна загрузки и оптимизации.
3.  **Безопасность**: API эндпоинты перехода статусов заказа требуют более жесткой проверки прав (Role + Order Ownership).

---

## 3. Продуктовый аудит (Marketplace Expert)

1.  **Liquidity Risk**: Исполнителям нужно портфолио для получения заказов. Без этого заказчики будут уходить в Telegram-чаты.
2.  **Trust Loop**: Система отзывов есть в коде, но визуально не акцентирована. Нужна сквозная видимость рейтинга.
3.  **Onboarding**: Слишком быстрый логин без подтверждения (SMS/OTP) — риск фейковых аккаунтов.

---

## 4. Критические проблемы

| Проблема | Приоритет | Описание |
| :--- | :--- | :--- |
| **Media Delivery** | **Critical** | Нет загрузки фото. В натяжных потолках замер без фото невозможен. |
| **152-FZ Compliance** | **High** | Нет чекбокса согласия с политикой конфиденциальности. |
| **Status Logic** | **High** | Заказчик может случайно откликнуться на свой заказ (или наоборот), если не разграничить UI. |
| **State Drift** | **Medium** | При смене роли в профиле UI других вкладок не узнает об этом мгновенно. |

---

## 5. План действий (Hardening Phase)

### Шаг 1: Медиа и Профили
*   Внедрить `portfolio` в модель `User`.
*   Добавить мульти-загрузку фото для заказов (multer).
*   Реализовать галерею в `OrderDetail` и `Profile`.

### Шаг 2: Унифицированный UX
*   Сделать вкладки общими.
*   Реализовать тумблер ролей в профиле.
*   Скрыть кнопку «Откликнуться» для режима Заказчика.

### Шаг 3: Стабильность и Парсинг
*   Внедрить Smart Parser V4 (Moscow locations, relative dates).
*   Добавить Recycle Bin для мягкого удаления заказов.

**Оценка: 7.8 / 10** (Технический фундамент отличный, не хватает production-обвязки).
