# Отчет по техническому и продуктовому аудиту проекта CeilingsApp

## 1. Краткое описание проекта

**CeilingsApp** — это специализированный маркетплейс, соединяющий заказчиков (работодателей) с частными мастерами и бригадами по установке натяжных потолков.
Приложение работает по модели "On-demand": заказчик размещает объявление, мастера в реальном времени получают уведомления на карте и откликаются. Система включает в себя управление жизненным циклом заказа, чат, систему рейтингов и портфолио.

## 2. Оценка проекта: 7 / 10

**Объяснение оценки:**
Проект имеет отличную архитектурную базу для масштабирования (реализованы гео-сетки для WebSocket, событийная модель логов, эффективное кэширование на фронтенде). Выбраны правильные технологии (NestJS, React Native, Prisma, PostgreSQL).
Однако, на текущий момент проект находится в стадии "Hardened MVP". Требуются доработки в области инфраструктуры (CI/CD, мониторинг) и окончательная полировка UX (реальные SMS-уведомления вместо заглушек).

## 3. Что сделано хорошо

*   **WebSocket Архитектура (V10)**: Переход на комнаты (Geo-Rooms и User-Rooms) — это стандарт индустрии для высоконагруженных гео-сервисов. Это решает проблему O(N²) при рассылке уведомлений.
*   **Синхронизация состояния**: Реализован механизм `syncAfterReconnect`, который гарантирует доставку пропущенных событий. Это критично для мобильных приложений с нестабильной связью.
*   **Smart Import (NLP)**: Эффективный парсер неструктурированного текста (WhatsApp/Telegram) значительно снижает барьер входа для заказчиков.
*   **Слоистая архитектура**: Четкое разделение на `Services`, `Stores` (EntityStore) и `UI` на фронтенде позволяет легко менять логику без переписывания экранов.

## 4. Критические проблемы

*   **Infrastructure (High)**: Отсутствует настроенный процесс автоматического деплоя и миграций БД в проде.
*   **Security (Medium)**: Отсутствует Rate Limiting на API, что делает сервис уязвимым к перебору телефонов или спаму заказами.
*   **UX (Medium)**: Нет реальной интеграции с SMS-провайдером для верификации (используется авто-логин).
*   **Testing (Low)**: Покрытие тестами (Unit/E2E) минимально, что может привести к регрессиям при быстром росте функционала.

## 5. Что нужно исправить в первую очередь (План действий)

*   **Шаг 1: Инфраструктурная обвязка**. Настроить Docker-контейнеризацию и GitHub Actions для автоматической сборки фронтенда и бэкенда.
*   **Шаг 2: Безопасность данных**. Внедрить Helmet.js и Rate Limiter на бэкенде. Ограничить количество запросов к эндпоинту `auth/login`.
*   **Шаг 3: Интеграция уведомлений**. Подключить Firebase Cloud Messaging (FCM) или Expo Push Notifications для доставки алертов в фоновом режиме.

## 6. Что улучшить в архитектуре

*   **Micro-Services (в будущем)**: При достижении 100k+ пользователей выделить сервис геолокации и чата в отдельные инстансы.
*   **Type Safety**: Полностью избавиться от `any` в бэкенд-сервисах, обеспечив 100% генерацию Prisma типов в CI-пайплайне.
*   **Caching Layer**: Добавить Redis для хранения горячих данных (активные комнаты WebSocket, сессии), чтобы разгрузить PostgreSQL.

## 7. Что добавить перед запуском

*   **Real SMS Provider**: Интеграция с сервисом (например, SMSRu или Twilio) для подтверждения входа.
*   **Moderation Tool**: Простая админ-панель для блокировки фейковых заказов и недобросовестных исполнителей.
*   **Payment Gateway**: Если планируется монетизация через комиссию или подписку (подписка уже заложена в схему, но требует интеграции с эквайрингом).

## 8. Итоговое мнение (CTO Perspective)

"Как CTO, я оцениваю проект как **жизнеспособный и перспективный для инвестиций**.
Технический фундамент заложен с запасом на рост до 50,000–100,000 пользователей. Код написан профессионально, критические ошибки (OOM, Race conditions) в последней версии устранены. Проект готов к переходу в стадию бета-тестирования на ограниченной группе пользователей после интеграции SMS-провайдера."
